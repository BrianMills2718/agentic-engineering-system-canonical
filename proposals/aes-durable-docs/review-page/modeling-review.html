1. Three things called "model"

Think of a house. A system model is the blueprint of one house. A framework is the rule for which drawings every house gets (floor plan, wiring, plumbing) and how each drawing is checked against the real building. A research metamodel is a theory of what any building is made of. All three were worked on, by different sessions.

A. One blueprint per repo (finished, everywhere)

Every governed repo now has a goal, requirements, a system model (prose plus docs/model/trace.yaml: rule → file that does it → test → decision) and decision records. Rolled out to 22 repos and checked daily.

B. The framework of drawings (half-built, hidden)

A catalogue of model kinds (domain, data flow, state machine, schema, run trace), each with a hand-written "intended" side and a generated "actual" side, compared by tests. The rules part landed in company-planning; the design write-up sits only on the unmerged AES branch shaping/model-framework.

C. Research metamodels (separate subject)

observation-to-action (what any analysis is made of) and fol-operational-metamodel (logic structure from standards). Not related to A or B, but they share the word "metamodel".

3. The words, defined once

Hand-written for now; the plan's generated glossary (R6) replaces it later.

WordMeans hereExample
ModelA description that leaves things out on purpose so one question is easy to answer.A subway map: it drops distances so "which line do I take?" is easy.
InstanceOne filled-in case of a model.A blank job-application form is the model; your filled-in copy is an instance.
MetamodelA model whose instances are models: the rules for what a model may contain.UML's rulebook says a class diagram has boxes (classes) and lines (associations); each class diagram is an instance of it.
System modelOne repo's blueprint: its things, its steps, its rules, and which code writes which records. File: docs/model/ARCHITECTURE.md."Rule: a commit needs a plan tag. Done by commit_rule.py. Proved by test_commit_rule.py."
Trace fileThe machine-checked list behind the system model: rule → file that does it → test → decision. File: docs/model/trace.yaml.The checker fails if the named test file was deleted.
Intent modelThe model of one slice, each piece marked "decided" or "guessed", with status computed from recorded test runs.qualitative_coding docs/model/slice1/intent.md.
Framework (megamodel)The rule for which kinds of model a repo gets and how each is checked against the code.Every repo gets a domain model and a data-flow model; each has an intended version and a generated one, compared by a test.
arc42A standard outline for architecture documents (goals, context, runtime, decisions, glossary ...). Our system model uses its section names.Section 1 "Introduction and Goals".
C4A standard set of diagrams by zoom level: system, containers, components, code.Zoom from "AES talks to GitHub" down to the classes in one module.
ODDOverview, Design concepts, Details: an outline made for describing simulations. Replaced by arc42 + C4 for software on 10-10.Still the right outline for an agent-based simulation.
ZachmanA grid for sorting architecture descriptions: six questions (what, how, where, who, when, why) by six viewpoints. It sorts models; it does not say how to check them.Our system model fills roughly the what, how and why cells at the builder's row.
DoDAFThe US defense architecture framework: a fixed set of required views plus a metamodel linking them.Used in the dodaf repo.
