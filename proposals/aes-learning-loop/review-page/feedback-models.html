Feedback system: what exists (domain model) and what moves where (data flow)

Two pictures of the same system. The domain model names each kind of thing and how they relate: a report holds records, records group into problems. The data-flow model shows which program moves what into which store, and when. Both are drawn from the code as of 12 October 2026; every box has a source in the table at the bottom.

Start here: the feedback loop guide. Companion page with live counts: the whole picture. Plan: feedback loop plan.

3. One real report, followed through both

  1. Agent reply. On 11 October, in this conversation, Claude ended a reply with a Feedback section. One line said a gate's block message still sends agents to the old place for friction reports, linking agent-skills/contracts/client-config/jev/worktree_guard.py.
  2. Session file. The reply was saved in Claude's session file for this conversation (store: Session files).
  3. Collector, 3:30 am. Read the new text, found the Feedback section, parsed the line by its obs (control): marker into one Observation record with one Evidence link, and wrote it to reports-2026-10-11.jsonl.
  4. Feedback log. The report was filed as issue #494 in agent-feedback-log.
  5. Sunday grouping. Next Sunday the record is tagged with the closest failure kinds (or "not a failure") and is paired with similar records. If another conversation saw the same thing, they join one Problem.
  6. Where it would go today. If that Problem repeats, it gets a cause analysis at the next weekly run (no cap since 12 October). Once analysed with an active licence, an adopt issue opens; the daily fix owner implements it or closes it with a reason, and leaves a receipt the effect counter reads the next morning.
