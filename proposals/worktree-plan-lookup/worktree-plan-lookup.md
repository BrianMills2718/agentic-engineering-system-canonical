## Success and disproof

> **CORE-SUCCESS-DISPROOF** (blocking): The plan defines the evidence that would show success and a concrete condition that would disprove the approach. Each success measure is the property the plan claims, or a check that directly tests that property, not a stand-in for it: a count, a picture, a readability judgment, or the pipeline agreeing with itself (hashes, labels, byte equality) does not show correctness or conformance it does not test. A plan fails this item if it has no disproof condition, or if a success measure is such a stand-in for the claimed property and the plan names no direct check of that property.

> **CORE-TRACE-REVIEW** (blocking): Every success or acceptance criterion in the plan is judged from the full trace of a run, not only its final outcome: it names the run whose full trace is examined (for example the session, its tool and LLM calls, commits, check output, or messages), where that trace lives, and what must be seen in that trace beyond the final outcome. A criterion that names only an outcome, such as tests passing, a PR merged, a test fixture reproducing the journey, or a status reading succeeded, fails this item. A criterion for which no run exists, such as a pure document edit, passes only when the plan states that exemption and its reason explicitly.

Success means distinct consumer and owner repositories stay distinct during lookup, the alternate caller index still contains its staged content, every affected foreign subprocess uses the documented isolation, and both installed consumer hooks retain their positive and negative admission behavior. Disproof: the hook reads a consumer's objects as the owner, loses a staged-only receipt, accepts an unknown plan, or an artifact claimed to follow Git's hook rule retains any documented repository-local variable during a foreign operation. No counts or cache hashes replace these behavioral checks.

All named runs append to `/home/brian/projects/data/logs/worktree-lifecycle-verification.log`; the Agent Skills observer also supplies its complete native-hook trace. Read every failed/surprising trace and a passing sample before reporting results.

Existing before-run has two failures: wrong owner SHA and absent background environment isolation.
- `local-merge-gate` / `standard-conformance-gate`: record exact candidate, commands, full test output and exit status, including any dependency-pin failure and its authentic pinned-fixture resolution. No unexplained failures count as success.
- `installed-planned-commit`: inspect loaded module path/revision, Project Meta's real staged cursor disposition, the immutable owner's plan and receipt, unmodified hook invocation and commit result. Inspect the actual owner and consumer identities, not only an index entry.
- `agentskills-installed-guard`: inspect the same ordinary installed hook before and after installation, acceptance of the adopted `aes-feedback-prevention` receipt, rejection of an unknown plan, and clean owned before/after state. The observer performs no source edits.

A plan with neither a model link nor the exemption line fails this item, as does one that lists model elements without saying what the examined run must show of each, or one that names no element without stating that the work touches none and why. For a maintained repository, the plan also cites the documentation entry point from which the model is reachable; a shared model explicitly identifies this repository's scope. This repair's scope is AES commit admission within that shared boundary. Existing entities are owner and consumer repositories; records are plan-index entries and adoption receipts; processes are foreign lookup/background refresh and local staged admission; the source-linked view is the existing `aes commit check` verdict in the ordinary hook.

For each process/source view, inspect these explicit observations in `foreign-git-context-regressions`: `_default_ref` returns the requested owner ref and SHA; `build_plan_index` records that owner's actual plan membership; `indexed_adoption` consumes that owner's receipt successfully; `_plan_text` returns that owner's actual plan content; `staged_adoption` consumes a receipt staged only in the alternate caller index; `_refresh_index_in_background` launches the ordinary index worker with all Git-local variables removed and PATH/SSH preserved. The relevant source views are `_default_ref`, `build_plan_index`, `_indexed_adoption`, `_plan_text`, `staged_adoption`, and `_refresh_index_in_background` in `commit_rule.py`.
