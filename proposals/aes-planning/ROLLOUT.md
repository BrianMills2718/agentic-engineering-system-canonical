## How the rule reaches every repository

`rollout/install_everywhere.py` (run with `install`, `check` or `uninstall`):

| Kind | Repositories (2026-10-07) | How the rule runs |
|---|---|---|
| global | no local `core.hooksPath` | one call to the generated `~/.config/git/hooks/_aes_commit_rule.sh` at the top of the global `commit-msg`; the original is kept as `commit-msg.before-aes` |
| local | a local `core.hooksPath` (the governed repositories' tracked `hooks/`) | `core.hooksPath` points at `~/.config/git/hooks-local/<repo>/`, whose `commit-msg` runs the rule then the repository's own hook and whose other hooks run the repository's own hooks unchanged; the original value is kept in `aes.originalHooksPath` |
| aes | hooks generated by `aes hooks install` | already run the rule |

The mode comes from a repository's `.aes/commit_rule.yaml`, or else the machine-wide
`~/.config/aes/commit_rule.yaml` (`mode`, trivial limits, and `repos: {<dir>: {mode: ...}}`
overrides). The installer writes that file in observe mode. The hooks run `aes` from
`uv tool install --from <AES main> agentic-engineering-system`; if `aes` is missing the hook
warns, logs to `~/.local/state/aes/commit-rule-missing.log` and lets the commit through.

`install_everywhere.py check` lists every repository and exits non-zero if any is unwired
or the runtime is missing, so a daily run says when the control has gone dark somewhere.
Undo: `install_everywhere.py uninstall` restores every `core.hooksPath` and the global hook.

Sandbox test before touching the real machine (two repositories, one of each kind, a stand-in
`aes`): install wired both; a refused message stopped the commit in both; a good one passed;
each repository's own hooks still ran; uninstall restored the global hook byte for byte.

## Replay: the last 300 commits of every active repository

`replay-2026-10-07.csv`: 185 repositories with a commit in the last 30 days, 21,948 commits,
judged by `aes commit replay` with today's rule.

| Verdict | Commits |
|---|---:|
| accepted | 308 (277 of them `[Trivial]`) |
| refused: no tag at all | 17,332 |
| refused: `[Plan #N]` naming a plan with no adoption receipt (or none found) | 2,238 |
| refused: `[Unplanned]` with no `Emergency:` line | 1,714 |
| refused: `[Trivial]` touching a running-thing file | 211 |
| refused: `[Trivial]` over 3 files or 60 lines | 145 |

**99% would be refused, and no repository is at or under 1 in 5.** The refusals are not the
rule misjudging small changes: almost no work in these repositories goes through an adopted
plan, and in 158 repositories more than 90% of commits carry no tag at all, which includes
commits made by scheduled jobs. Under the approved condition every repository therefore
stays in observe mode, and this goes back to Brian.

What would have to change before enforce is safe anywhere but AES canonical:

1. Scheduled jobs that commit (brain updates, wiki syncs, data refreshes) need a recognised
   tag or a measured exemption, or enforce stops them.
2. Each active project needs adopted plans for its real work, so agents have a `[Plan #N]` or
   `[Goal <id>]` that resolves; today only AES canonical's two plans are adopted.
3. The 2-day observe logs (`<repo>/.git/aes/commit-rule-<date>.jsonl`) measure today's work,
   which the replay of past work cannot; read them on 2026-10-09 before any switch.

## Federated plans and the misuse review (2026-10-07)

- **Plans live in the repository that owns them.** With `plan_workspace: ~/code` in
  `~/.config/aes/commit_rule.yaml`, a `[Goal <id>]` not found in the committing repository or
  the plan roots is looked up in every Git repository directly under `~/code` (front matter
  `plan_id: <id>`), so moving a plan out of AES canonical keeps its tags working. Measured: about
  1,700 plan files scan in under a second; a world-substrate plan named from personal-vps
  resolves in 0.26 s. `[Plan #N]` stays per repository.
- **What the 2026-10-07 live refusals were** (outside AES canonical, deduplicated by subject): of
  the plan-tag refusals, two were commits made before their plan was adopted or before the shared
  plan root existed (both resolve today), and the rest named ids that are not plans anywhere
  (`review-20261007`, a roadmap id; `vision-coverage`, a page with no `plan_id`). Those stay
  refused; the fix there is a plan, not a looser rule.
- **Misuse review** (`rollout/misuse_review.py`, timer `aes-commit-misuse-review` at 07:30): the
  rule accepts `[Unplanned]` on any `Emergency:` line and `[Trivial]` on counts alone; each night a
  light model (Jev via llm_client) judges yesterday's accepted ones (real emergency? behaviour
  change?), logs every verdict to `~/.local/state/aes/commit-misuse-review.jsonl`, and opens the
  keyed concern `aes-commit-tag-misuse` for p ≥ 0.8. Report-only; it never blocks a commit. First
  run (2026-10-07): 17 judged, 2 flagged, 11 skipped (smoke tests never committed, squashed
  branches, a duplicate folder), $0.001, 45 s, issue #188. Both flags were right on reading (a
  cursor-tag behaviour change; the C: reserve lowered from 30 to 20 GiB); of four `[Unplanned]`
  commits read by hand, three stated real emergencies and one (a plan-adoption blocker) is debatable.
